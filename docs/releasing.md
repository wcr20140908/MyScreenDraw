# 构建与发布 / Building and releasing

**当前源码：v6.0.1 修复候选，待发布与验收**。更新器实现仍在修改，本页是发布流程与验收要求，不是构建、测试或发布成功声明。本轮证据统一填写到 [6.0.1 验证记录](release-validation-6.0.1.md)，不得借用旧包证据。

历史状态：v6.0.0 已发布，公开 ZIP 和校验文件曾回下载核对、解压 EXE 曾通过离屏启动检查；这些结果只属于 6.0.0。README 的下载与校验链接暂时保留 6.0.0，6.0.1 正式附件发布并核验之前不要切换。

## 准备构建

使用 Windows x64 和 Python 3.11 开发基线，先按 [贡献指南](../CONTRIBUTING.md) 创建虚拟环境：

```powershell
python -m pip install -r requirements.lock -r requirements-build.lock
python -m pip install pytest pytest-subtests
.\build.ps1
```

运行前确认 `build/` 和 `dist/` 没有需要保留的数据：脚本会清理这些目录。测试工具当前没有独立锁文件，应在验证记录中注明实际版本；不要声称整个环境已完全锁定或二进制可逐字节复现。

## 脚本实际做什么

1. 校验 `version.py` 与脚本中的版本门禁一致（当前锁定 `6.0.1`）。
2. 执行离屏 pytest 门禁，排除真实触控层。
3. 使用 `MyScreenDraw.spec` 生成无控制台、禁用 UPX 的 onedir 包。spec 在依赖分析期间将 System32 放在 PATH 前，避免外部工具的同名系统 DLL（例如不兼容的 ICU）污染产物；分析结束后恢复环境。
4. 检查许可证、Qt 平台/图片/PDF/SVG 依赖，并拒绝用户数据、截图、源码和运行日志混入。
5. 执行构建目录中的 `--smoke-ui`，在函数内强制 Qt offscreen 并禁用软键盘启动，异常时也恢复调用方环境；清理验证产生的运行数据。
6. 写入 `RELEASE-MANIFEST.json`，包含应用版本、EXE SHA-256 和当前 `signature: none` 状态。
7. 打包 ZIP（排除 `data/`、`exports/`），执行 `release_artifact.py` 归档校验，再比对全部解压文件，并以同样的 offscreen 保护验证 EXE 启动与哈希。
8. 全部检查通过后，候选 ZIP 才提升为正式文件名，同时保存 `.sha256` 和 `build/release-receipts/` 下的验收收据。收据绑定包、EXE 及打包源码；不是数字签名。

成功构建后预期输出为 `dist/MyScreenDraw/`、`MyScreenDraw-v6.0.1-windows-x64.zip` 和同名 `.zip.sha256`。ZIP 根目录必须直接包含 `MyScreenDraw.exe`、`_internal/`、许可证和清单；不能额外套一层目录，也不能上传源码 ZIP 冒充便携版。

构建成功不等于实屏验收通过，也不会自动发布 GitHub Release。发布脚本要求干净工作树、指定提交等于 HEAD、远端提交存在，以及源码、清单、校验文件和验收收据一致；不会重写校验文件来认可未经验收的包。源码或构建脚本改变后需要重新打包，验证报告等文档可以在构建后补齐再提交。

## 下一版本必须同步的文件

- `version.py`：应用版本来源。
- `version_info.txt`：Windows 数值版本和完整 ProductVersion 字符串。
- `build.ps1`：硬编码版本门禁。
- `create_release.ps1`：版本门禁、标签、release notes 路径与 prerelease 标记。
- 中英文 README：源码版本与发布状态；便携下载链接及校验示例只指向已发布附件。
- `CHANGELOG.md`、对应版本的 release notes、`SECURITY.md`。
- 本页及其他描述“当前基线”的维护文档。

不要批量替换历史 release notes 的版本号。预览标签和 GitHub prerelease 标记应一致；正式版不能仍被标为预览。打包产物通过 Release 附件分发，不提交二进制包或用户数据到 Git。候选阶段保留当前正式版 release notes，并新增下一版候选说明；不要删除或改写历史证据。历史清理记录：2026-10-03 已删除 v6.0.0-beta.1 至 beta.8 的说明文件。2026-10-05 已删除 GitHub 上全部 7 个预览版 Release（v5.0.0-beta.1、v6.0.0-beta.3 至 beta.8），包括发布说明、便携包和校验附件；正式版 Release、Git 标签及提交历史保留。历史变更见 `CHANGELOG.md`。

## 每次正式版发布验收清单

以下为每个最终候选包重新核对的验收清单，不代表所有环境均已覆盖。6.0.1 各项均须提供本候选证据，见 [当前验证记录（待填）](release-validation-6.0.1.md)；[6.0.0 验证记录](release-validation-6.0.0.md)只供历史参考：

- [ ] 冻结功能；不存在已知的数据丢失、核心输入失效、崩溃或严重性能阻塞问题。
- [ ] [离屏回归](testing.md)通过，逐项解释跳过及未运行的测试。
- [ ] 最终 EXE 在目标触控大屏完成批注、鼠标穿透、多指、菜单、文字公式、白板和托盘验收。
- [ ] 用旧版配置和项目验证升级、独立笔形迁移、保存恢复；保留回退所需的数据备份。
- [ ] 验证下载失败、文件占用或权限失败时的更新行为，不损坏旧程序与用户数据。
- [ ] 完成长时间课堂使用和复杂页面压力验证。
- [ ] 记录 Windows 10/11、DPI 缩放、多屏、中文/空格路径、普通用户权限、无 Python 环境的实际覆盖范围。
- [ ] 验证断网及更新接口不可达时仍可启动和绘图。
- [ ] 校验便携 ZIP 内容、哈希、许可证、隐私清理和真实解压启动。
- [ ] 确认已知导出限制及未签名状态在用户文档中可见。

## 6.0.1 更新器专项门槛（待实现核对与验收）

- [ ] 下载状态独立于检查状态；下载期间重复检查或关闭设置不应错误清除下载状态或产生并行安装。
- [ ] 已知可信总大小显示百分比与字节进度；总大小未知时显示不定进度与已下载字节，不伪造百分比；下载结束仍须完成归档验证。
- [ ] 取消、网络失败、下载完成及校验失败各自正确清理状态和临时文件，取消后不进入安装，不改用户文件。
- [ ] 源码运行目录明确拒绝应用内覆盖安装，不改源码工作树。
- [ ] 便携安装传递目标版本与旧 PID；安全等待正确的旧进程完全退出。超时、无法确定进程身份或退出被取消时不得继续覆盖，不能以同名进程批量结束替代定向等待。
- [ ] 新 EXE 版本匹配目标，重启结果可验证；版本不符、重启失败、文件占用和权限失败等路径触发适当回滚并保留诊断，不能只凭启动命令已发出就宣布成功。
- [ ] 成功、取消和失败回滚均保留 `data/`、`exports/`、配置、名单、日志、自动保存及其他隐私文件；使用合成数据和前后哈希验证，不把真实数据装入包。
- [ ] 单独验证 **6.0.0 → 6.0.1 手动换目录迁移**。6.0.0 的运行中更新器有缺陷，新包不能追溯修老的下载/安装代码；不能将用新源码更新器跑通的事务作为旧版应用内升级成功的证据。

发布说明必须明确：从正式 Release 手动下载并校验 6.0.1，解压到新目录；完全退出旧版后备份并复制 `data/`、`exports/`，不覆盖隐私文件；修改快捷方式及已启用的开机自启路径，运行新 EXE 并核对版本与重启。正式发布前使用条件式说明，不放尚不存在的附件直链。

## 发布后验证

发布前先复核 `release-notes-v6.0.1.md` 候选草稿及本轮验证记录，不能把计划中的修复、历史日志或空白待填项写成最终通过。由发布负责人补齐具体命令、退出码、通过/失败/跳过数量、包哈希和必要的交互证据后，按实际结果修订对外说明。

只有 6.0.1 正式附件发布并回下载核验后，才将中英文 README 的下载/校验示例、支持版本表及候选状态切换为正式；保留 6.0.0 手动迁移警告，不把已发布 6.0.0 描述为含有 6.0.1 修复。历史上，6.0.0 的下载入口也在附件发布并核验后才完成切换。

从 GitHub Release 下载实际附件，不要只检查本地构建目录。比对 ZIP SHA-256，在新目录解压验证启动，确认版本显示、EXE 和 `_internal` 完整。Release 首屏和 README 提供便携 ZIP 直链，并明确 GitHub 自动生成的 Source code 附件不能直接运行。

签名策略见 [代码签名说明](code-signing.md)。仅更新文档或创建 commit 不会更新已发布 ZIP；不要声称旧附件包含后来改动。
